01背景と方針

LINEの投票機能は、各投票者の投票日時を取得できない。一方で、参加者に馴染みのない新しいアプリを配ると、操作の学習コストと脱落が発生する。特に今回の対象は高齢の参加者が多く、アプリの切り替えや文字入力が大きな障壁になる。

そこで、見た目と操作をLINEの投票機能に揃えたうえで、タイムスタンプを記録できる別アプリを用意する。参加者の体験は可能な限り現状のまま、研究に必要なデータだけを追加で取得する。

設計の優先順位

  1. 参加者の操作を増やさない — ログイン、文字入力、アプリ切り替えをゼロに近づける。ここを削るほど脱落が減る。
  2. 時刻の精度を落とさない — 測定対象がタイミングそのものなので、サーバー応答の遅延はそのまま測定誤差になる。
  3. 見た目をLINEに寄せる — ただし著作物の複製はしない（5章）。

主要な観測変数は意思決定のタイミングである。誰がいつ投票したかに加え、開いてから決めるまでの時間、開いたのに投票しなかった離脱を記録する。いずれもLINEの投票機能では取得できない。

02検証済みの事実

最大の技術的リスクは「オープンチャットではLINEアカウントによる個人識別ができないのではないか」という点だった。実機検証の結果、回避可能であることが確認できた。

確定オープンチャットでもLINEログインは通る

LIFF（LINE Front-end Framework）はオープンチャットで公式サポートされておらず、プロフィール取得が動かない。しかしLIFFを使わず、汎用のLINEログイン（OAuth 2.1）を直接実行すれば識別できる。両者は別の仕組みであり、LIFFの制限はOAuthフローには及ばない。

自動ログイン（2回目・アプリ完全終了後）成功 / 2068ms / 無操作同上
実行環境の判定LINE内ブラウザオープンチャットから起動
localStorage / sessionStorage / Cookie3系統とも生存アプリ完全終了を跨いで保持

参加者はリンクをタップするだけで本人が特定される。ログイン画面もパスワード入力も外部ブラウザへの遷移も発生しない。設計の前提条件はこれで満たされた。

要追加検証まだ1台・1名の結果である

比較的新しいiPhone 1台での成功にすぎない。古いAndroid、長期間LINEに再ログインしていない端末、プライベートブラウジング設定では自動ログインが失敗しうる。

実装と並行して、協力者5〜10名（Android混み）で失敗率を測る。失敗率が5%か30%かで、識別失敗時の扱いの重みが変わる。

03参加者の動線

投票1回あたりの流れを、時刻の記録点とあわせて示す。

1
作成者が投票を作る

固定URLを開く → 投票を作成 → 完了。この時点ではまだ誰にも見えていない。

2
作成者がURLをオープンチャットに貼る

ここが刺激提示時刻 T0。すべての潜時はこの時刻を起点に計算する。アプリ側は「投稿しました」ボタンで明示的に記録する（5.5）。

3
参加者がリンクをタップ

LINE内ブラウザが開く → 自動ログイン（無操作・約2秒）→ 投票画面。記録：開封時刻

4
選択肢を選んで確定

記録：投票時刻・選択内容。確定せずに閉じた場合も離脱として記録する。

5
作成者が締め切る

手動、または設定した終了日時で自動。記録：締切時刻

URLは常に同じものを使う

投票ごとに別URLを発行せず、研究グループに1つの固定URLを割り当てる。参加者は毎回同じリンクを開き、一覧画面から進行中の投票に入る。LINEの「グループの投票タブ」に構造が近くなり、URLの貼り間違いも防げる。

要確認

05LINE準拠できない点・要判断の点

この章が本設計書の中心である。「全部LINE準拠」という方針に対して、技術的に不可能なもの、法的に避けるべきもの、研究設計上そのまま真似ると問題になるものを挙げる。

5.1グループへの自動転送はできない不可能

LINEの投票は作成完了と同時にトークへカードが流れるが、これはLINE本体の機能である。オープンチャットにはボットを参加させられないため、外部アプリからメッセージを送る手段が存在しない。LIFFの liff.sendMessages() もオープンチャット非対応。

代替案：コピー＆貼り付け＋OGPカード

完了画面に「コピーする」ボタンを置き、定型文とURLを1タップでクリップボードに入れる。作成者はトークに貼り付けるだけ。操作が1つ増えるが、増えるのは作成者だけで、100名の参加者側の負担は変わらない。

見た目については、貼り付けたURLをLINEが展開するプレビュー（OGP）で再現できる。og:title に「[投票] 質問文」、og:description に「投票にご参加ください。」、og:image に自作の投票箱画像を設定すれば、画像5にかなり近いカードになる。

要検証：オープンチャットでURLプレビューが展開されるか。展開されない場合はテキストのみの案内になる。

5.2キャラクター画像は使用できない法務

画像1の熊のイラスト、画像5のブラウンとコニーは、いずれもLINEの著作物である。複製すると著作権・商標の問題が生じ、論文にスクリーンショットを掲載する段階で必ず問題になる。

一方、レイアウト・操作フロー・配色は一般に問題になりにくい。緑（#06C755）を基調にした画面構成、角丸のカード、丸い＋ボタンといった「雰囲気」レベルの類似は維持してよい。

対応：投票箱の抽象アイコンを自作し、キャラクターの位置に置く。他のLINE固有アセット（ロゴ、スタンプ）も一切使わない。

5.3「匿名投票」オプションは危険倫理

本設計書で最も重要な指摘

LINEの「匿名投票」は他の参加者に投票者が見えないという意味である。しかし本アプリでは、匿名投票を選んでもサーバーには userId とタイムスタンプが記録される。研究の目的上、記録しないという選択肢はない。

参加者が「匿名＝記録されない」と解釈する可能性は高く、実質的に同意を得ないままデータを取ることになる。倫理審査で確実に指摘される。

推奨：オプション自体は残すが、ラベルを「投票した人を他の参加者に見せない」に変更し、同意画面にも「誰がいつ投票したかは研究のため記録されます」と明示する。ラベルの変更だけで誤解の大半は防げる。

5.4「選択肢の追加を許可」は分析を複雑にする要判断

参加者が選択肢を追加できると、選択肢の集合が時間とともに変化する。「その人が投票した時点でどの選択肢が存在したか」を追跡しないと分析できなくなり、後から選択肢が増えたことで投票を変更する人も出る。意思決定タイミングの研究としては交絡が一段増える。

推奨：UIには残す（LINE準拠のため）が、作成時のデフォルトをOFFにし、実験用の投票では使わない運用とする。イベントログには option_added を記録しておき、万一使われても追跡できるようにする。

5.5通知が送れないため、刺激提示時刻を別途記録する設計

ボットが使えないため、投票開始のプッシュ通知は送れない。参加者が投票の存在を知るのは作成者がURLをトークに貼った瞬間である。投票の作成時刻とは一致しない（作成してから貼るまでに時間が空く）。

潜時をすべて T0 起点で計算するため、この時刻を正確に押さえる必要がある。完了画面のコピーボタンとは別に、「グループに投稿しました」ボタンを置き、押された時刻を poll_published として記録する。

5.6途中経過をどこまで見せるか最優先

スクリーンショットで判明：投票する前から結果が見えている

画面Fはまだ投票していない状態だが、すでに各選択肢の票数とバー、そして「N人が参加中」が表示されている。つまりLINEの投票では、参加者は他人の選択を見てから自分の選択を決める。

100名規模でこれをそのまま再現すると、「60人が既にAを選んでいる」という情報が全員に届いた状態で意思決定が行われることになる。意思決定タイミングの研究において、これは無視できる大きさの影響ではない。主要な交絡要因にも、主要な観測対象にもなりうる。

この判断は他のどの未決事項よりも先に決める必要がある。データを取り始めてからでは条件をやり直せない。

案内容研究上の含意
LINE準拠誰が何に投票したか全員に見せる再現度は最高。同調が支配的要因になりうる
人数のみ「N人が投票済み」だけ表示し内訳は隠す参加動機は残しつつ、選択肢への同調を防ぐ
完全に隠す締切まで一切見せない他者の影響を排除。LINEとの差が最大
条件操作投票ごと・参加者ごとに切替影響そのものを測定対象にできる。実装は重い

実装方針：投票ごとの設定フラグ show_progress として持たせ、どの案でも切り替えられる形で作る。決定は画面Fのスクリーンショットを見てから行う。

5.7その他の相違点

項目扱い
投票の変更LINEは投票後の変更が可能。変更履歴は研究上価値が高いので、上書きせず vote_changed として追記する
LINE表示名の取得LINEログインで取れるのは実アカウントの名前とアイコンで、オープンチャットの表示名とは別物。参加者が匿名性を期待している場合、実名が研究者に見えるのは問題になりうる。既定では保存せず、userId のみを保持する

テーブル主なカラム役割

時刻の扱い

  • サーバー受信時刻（UTC・ミリ秒）を正とする。クライアント時計は信用しない。
  • クライアント時刻も client_ts に併記し、差分から端末の時計ズレを検出できるようにする。
  • 「開いた」の定義は投票画面が実際に表示された時点とする。認証リダイレクト中は含めない。
  • バックグラウンドからの復帰は page_hidden / poll_opened の対で表現する。

07認証と権限

  1. 参加者が固定URLを開く
  2. サーバーが LINE の認可URLへリダイレクト（自動ログイン・無操作）
  3. 認可コードを受け取り、サーバー側でチャネルシークレットを使ってトークンに交換
  4. IDトークンを検証して userId を取得
  5. 署名付きの HttpOnly Cookie でセッションを維持

クライアントで取得したプロフィールをそのままサーバーに送る実装はしてはならない（改ざん可能で、作成者権限の偽装につながる）。必ずIDトークンをサーバーで検証する。

権限できること
作成者投票の作成、締切、結果の全件閲覧、CSV書き出し。polls.created_by と一致する userId のみ
参加者投票、投票の変更。設定に応じた途中経過の閲覧

要設計初回に見せる2つの画面

参加者が初めてアクセスしたとき、LINEの権限許可画面（1タップ）と研究参加の同意画面が続けて出る。高齢の参加者にとって唯一の関門であり、ここでの離脱がそのまま欠測になる。

文言と画面設計は別途詰める。実際の権限許可画面がどう見えるかは、連携アプリの登録を解除して実機で確認しておく。

識別に失敗しても投票は通す

自動ログインが失敗した参加者に、メールアドレス入力を求めてはならない。そこで確実に脱落する。ログインに失敗した場合は識別を諦めて投票させ、端末ベースの仮IDと「未識別」フラグを付けて記録する。

これは実装の都合ではなく妥当性の問題である。ログインに失敗するのは古い端末や特殊な設定の層で、年齢や情報リテラシーと相関しうる。彼らを除外すると、測定対象である意思決定タイミングと相関した欠測が発生する。全員から投票を取り、識別できた分でメイン分析、できなかった分で脱落バイアスを検証する。

08システム構成

層採用理由
実行環境Cloudflare Workersコールドスタートが実質ゼロ。時刻記録に遅延ノイズが乗らない。100名の同時アクセスにも余裕
データベースCloudflare D1（SQLite）無料枠で書込1日10万行・容量5GB。プロジェクトが自動停止しない
フロントCloudflare PagesAPIと同一ドメインに揃えるとCookieの扱いが単純になる
認証LINEログイン v2.1LIFFは使わない（オープンチャット非対応のため）

Supabaseは無料プランだと7日間アクセスがないとプロジェクトが自動停止するため、投票が散発的な研究運用には向かない。Google Apps Scriptはコールドスタートが数秒あるうえ、ウェブアプリのURLがリダイレクトするためLINEログインが要求するコールバックURLの完全一致と相性が悪い。いずれも上の2つの理由で見送る。

8.1差し替え可能にしておく層

モック段階ではデータベースを繋がず、この層の中身をメモリ上の配列にしておく。本番では同じ関数がAPIを叩くようになり、UI側のコードは変更しない。

// data.js ── 画面側はこの関数しか呼ばない
export async function listPolls()                  { ... }
export async function getPoll(pollId)              { ... }
export async function createPoll(draft)            { ... }
export async function castVote(pollId, optionIds)  { ... }
export async function closePoll(pollId)            { ... }
export async function logEvent(type, payload)      { ... }

モックでは画面の隅に「今は誰として操作中か」の切り替えを置く。1人で複数の投票者を演じられるので、研究仲間への説明時に同調の見え方をその場で実演できる。イベントログも画面に流しておくと、取得できるデータを直接見せられる。

09未決事項

変更コストは、データを取り始める前なら安い。実験開始後に変えられないものから順に決める。

項目変更コスト必要な判断
記録するイベントの種類 高い 実験開始後は過去に遡れない。6.2の一覧で漏れがないか確認
匿名投票オプションの扱い 高い 同意文と一体。倫理審査の前に確定させる（5.3）
途中経過の可視性 高い 最優先。投票前から結果が見える仕様と判明したため、影響が想定より大きい。モックの3モードを比較して決める（5.6）
「投票を終了」を誰に見せるか 安い 作成者のみを推奨。実物の挙動が確認できれば準拠に戻せる（5.8）
終了後の画面仕様 安い スクリーンショット未提供。モックでは結果を確定表示している
研究同意の取得方法と文面 高い 100名からどう同意を得るか。アプリ内の初回画面で完結させるか、別途行うか
LINE表示名を保存するか 中 既定は保存しない。個人の特定が必要なら初回に自己申告を求める（5.7）
自動ログインの失敗率 安い 協力者5〜10名で実測。実装と並行で可
OGPカードの展開可否 安い 実機で1回試すだけ（5.1）
デザインの細部・配色 安い いつでも変更可
データベースの選定 安い 差し替え層があるため後から変更可（8.1）
